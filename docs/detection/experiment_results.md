# 실험 결과: COCO / Roboflow / H250 베이스라인 vs 파인튜닝 비교

## 실행 조건

- **평가 대상**: coco / roboflow / h250 3개 모델 x baseline / finetuned 2단계 = 6개 조합
- **평가 방식**: `evaluate.py --all` (모든 모델 및 단계에 동일 코드, 동일 파라미터 적용)
    - 주 지표: mAP50 / mAP50-95 / mAP75 (torchmetrics 기반, confidence 전체 스윕)
    - 보조 지표: Precision / Recall / F1 (conf=0.25, iou=0.5 고정)
- **GT 규모**: val set 26장(전체 130장 중 20%, `split_dataset.py` 기본 val_ratio=0.2 기준),
    총 209개 바운딩 박스(이미지당 평균 8.0개, 모든 모델 및 단계에서 동일)
- **클래스 매핑**: baseline 3개 모델은 각자의 원래 클래스 체계를 
    `pretrained_class_map`으로 GT 단일 클래스(player=0)에 리매핑해 평가
    (COCO: person->player, Roboflow: goalkeeper+player->player, H250: person->player)
- **실행**: `python -m src.detection.evaluate --all`
- **재현**: 단일 실행 (seed 고정 없이 1회)

| 구분 | mAP50 | mAP50-95 | mAP75 | Precision | Recall | F1 |

| coco_baseline | 0.8618 | 0.5514 | 0.5714 | 0.8125 | 0.8708 | 0.8406 |
| coco_finetuned | 0.9952 | 0.7856 | 0.9207 | 0.9244 | 0.9952 | 0.9585 |
| roboflow_baseline | 0.6424 | 0.3857 | 0.4338 | 0.6825 | 0.6172 | 0.6482 |

## 관찰

**1. 파인튜닝은 세 모델 모두에서 뚜렷한 개선을 보임**
- 3개 모델 모두 baseline->finetuned 비교에서 mAP50-95가 개선됨 (평균 +0.28, 범위 +0.15~+0.45로 roboflow가 가장 크게 개선됨)

**2. 베이스라인 단계의 모델 간 격차가 컸음**
- h250(0.9459) > coco(0.8618) > roboflow(0.6424) 순으로 mAP50-95 격차가 큼
- H250이 SoccerNet(축구 도메인) 데이터로 사전학습된 반면, roboflow는 다른 축구 데이터셋 스타일로 학습되어 우리 방송 영상 도메인과의 괴리가 컸을 가능성이 있음(이는 두 모델의 사전학습 데이터 자체를 직접 비교분석한 결과가 아니라 현재 결과로부터의 추정임)

**3. 파인튜닝 후에는 세 모델이 거의 수렴함**
- mAP50 기준 0.9878~0.9952로 baseline 단계의 격차(0.64~0.95)에 비해 크게 좁혀짐
- baseline mAP는 "모델이 원래 얼마나 좋은 성능을 보이는지"보다 "사전학습 도메인이 타겟 도메인과 얼마나 가까운가"를 더 크게 반영할 수 있어, baseline 성능만으로 파인튜닝 후 최종 성능을 예단하기는 어려움

**4. mAP50과 mAP50-95의 격차가 큼**
- 파인튜닝 후에도 mAP50(~0.99)에 비해 mAP50-95(~0.78~0.83)는 상대적으로 낮음
- 이는 "선수가 있다는 것"은 거의 놓치지 않지만, 바운딩 박스 위치를 IoU 0.75~0.95 수준으로 정밀하게 맞추는 데는 아직 개선의 여지가 있다는 뜻

**5. Recall이 Precision보다 전반적으로 높음** 
- roboflow_baseline을 제외한 5개 조합에서 Recall이 Precision보다 높게 나타남
  (Precision 0.8125~0.9668, Recall 0.8708~0.9952)
- 이는 TP가 같을 때 GT_count(209)보다 Pred_count가 더 많다는 것과 동일한 사실이며(실제로 6개 조합 중 5개에서 Pred_count > GT_count), 모델이 선수를 놓치는 경우보다 오탐(false positive)을 만드는 경우가 상대적으로 많다는 뜻

## 한계

**1. val set 규모가 작음**
- 전체 130장 중 val 26장(GT 209개, 이미지당 평균 8.0개)로, 표준 벤치마크(COCO val 5000장, Pascal VOC 수천 장 단위) 대비 크게 작음
- 표본이 작을수록 개별 프레임 한 장이 전체 지표에서 차지하는 비중이 커지므로 우연히 혼잡한 장면이나 특정 카메라 각도(줌인/광각)가 몰려 있었다면 그 특성이 상쇄되지 않고 그대로 지표에 반영됐을 가능성이 있음

**2. 파인튜닝 결과가 과적합 신호일 가능성을 배제할 수 없음**
- 파인튜닝 후 mAP50이 세 모델 모두 0.98 이상으로 매우 높게 나옴
- train set 규모(104장)도 작고, epoch 수(50)로 데이터가 적은 상태에서 반복 노출이 많으면 val set의 특징(카메라 앵글, 조명 등)을 암기했을 가능성이 있음
- 이 수치를 실전 성능으로 곧바로 일반화하기 보다는 **같은 경기/영상 소스가 아닌 새로운 영상**에서 재검증이 필요함

**3. 단일 실행 결과임**
- 학습에는 랜덤성(가중치 초기화, augmentation 순서 등)이 있어 같은 설정으로 재학습해도 수치가 달라질 수 있음
- 단일 실행(seed 고정 없이 1회 학습) 결과라 학습 시드에 따른 변동성은 별도로 확인되지 않음
- 여러 seed로 반복 학습 후 평균과 표준편차를 보고하면 더 견고할 수 있음

**4. baseline 간 편차의 원인**
- roboflow는 원래 goalkeeper와 player를 구분하도록 학습된 모델이라(coco/h250은 사람을 세분화하지 않고 person 하나로만 다룸) 이 둘을 서로 헷갈려 잘못 예측할 여지가 있었을 가능성이 있음
- 이는 모델이 원래 다루던 클래스 세분화 수준의 차이에서 비롯된 것으로 볼 수 있음
